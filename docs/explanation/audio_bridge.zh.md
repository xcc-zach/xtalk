# 音频桥接模型

*实验中的功能*

X-Talk 可以在浏览器端把多个前端会话接到同一条共享音频总线上，让 bot 听到的是一条连续音频流，而不只是麦克风输入。bridge 完全是前端构件：共享总线通过 `createAudioBridge()` 创建，每个 bot 会话通过 `inputConfig.mode = "web_bridge"` 读取它，用户麦克风可以选择由 bridge 直接接入，bot 的输出音频会重新发布回 bridge，从而让其他 bot 继续听到并回复。

## 适用场景

Web 音频桥接适合需要在同一个浏览器页面里做到下面几件事的场景：

- 同时连接多个 X-Talk 会话；
- 让 bot 回应其他 bot 的语音输出；
- 可选地把真实用户麦克风音频也注入同一条共享流；
- 保持现有服务端接口不变，把音频编排放在前端完成。

由于路由发生在页面内，服务端把每个 bot 都视为一个带音频输入的普通会话，没有任何服务端配置会区分桥接会话与麦克风会话。

## 共享流模型

bridge 内部维护一条 `16000` Hz 的连续 PCM 音频流。

- 没有人说话时，这条流持续输出静默；
- 用户或 bot 发布音频时，这些音频被混入这条共享流；
- 所有配置为 `mode: "web_bridge"` 的 bot 会话都持续收到来自同一条共享流的音频帧，但收不到自己刚发布回去的那一路音频。

因此 bridge 避免了 bot 音频的点对点路由：所有发布者都往一条总线上写，所有 bridge bot 都从这条总线上读，每个 bot 自己发布的音频会从其本地输入流中过滤掉。自我过滤让 bot 不会把自己的回复当作新输入；共享混音则让任意数量的参与者加入时无需重新配置其他参与者。

共享混音带来的一个结果是：把输出写回流的 bot 可能会无休止地互相回答，停止这种交流由页面负责。
